# 響應式／流體排版

> 來源：Utopia（utopia.fyi，Trys Mudford／James Gilyead 的公開方法論）＋
> web.dev 的 fluid typography 說明。都是**公開方法論，非 skill 檔案照搬**，
> 只取跟框架無關的通用原則，接回本 repo 既有 token 系統。本 repo 的
> `site/`／`site-mobile/` 雙版本結構用得到。

## 一、斷點 vs 流體：兩者分工，不是二選一

- **版面骨架的重排**（單欄↔雙欄、側欄收合、tabbar 出現）用**離散斷點**
  （media query / container query）。版面結構的改變是跳變，不該「漸變」。
- **尺寸類的連續縮放**（字級、間距、圓角）用**流體**（`clamp()`），在
  最小／最大視窗寬之間平滑內插，省掉一堆中間斷點各調一次 `font-size`。
- 判斷法：這個數值「跨斷點時應該突然變」還是「應該跟著視窗連續變」？
  前者用斷點，後者用 clamp。

## 二、clamp() 的正確寫法（可抄的骨架）

```css
/* clamp(最小值, 隨視窗連續變的值, 最大值) */
font-size: clamp(1rem, 0.8rem + 1.2vw, 1.5rem);
```

- **中間項一定要有 `rem` 成分，不能純 `vw`**：純 `vw` 的文字在使用者放大
  瀏覽器字級時「完全不會變大」（vw 只跟視窗寬有關，無視使用者字級設定），
  等於踩死無障礙；混入 `rem` 才會同時respond 視窗寬 **和** 使用者縮放。
  （web.dev fluid type 同一個提醒。）
- 最小／最大值用該版本既有 type scale 的既有階，不要為了 clamp 另外發明
  新的 px 端點——**端點值一樣受第一層 token 鐵則約束**。
- clamp 語法難手改，算好就不要手動微調中間項；要調就整條重算。

## 三、mobile-first：預設寫窄螢幕，往上加

- 基礎 CSS 寫手機樣式（不包在 media query 裡），用 `min-width` 往上疊桌機
  差異，不要反過來用 `max-width` 往下砍——往下砍容易漏掉中間尺寸、且
  手機（流量多、裝置弱）不該先載入桌機樣式再覆蓋。
- 本 repo 已有 `site/` 與 `site-mobile/` 實體分版的，仍遵守各自版本內
  mobile-first 的疊加順序，不要在單一檔案裡桌機樣式當預設。

## 四、container query：元件自適應，不綁視窗

- 一個卡片／side module 可能同時出現在寬主欄和窄側欄——它該依**自己容器
  的寬度**決定單欄或雙欄，不是依視窗寬。這種情況用 `@container` 而非
  `@media`，元件才能到處重用不出錯。
- 用法：容器設 `container-type: inline-size`，子元件用 `@container (min-width: …)`。
  一樣只調結構／尺寸，顏色陰影仍走既有 token。

## 五、觸控人體工學（手機/平板）

- 點擊熱區最小 44×44px（呼應第三層的 40px，取兩者較嚴的 44）；相鄰可點
  元素之間留至少 8px 間隙，避免胖手指誤觸。
- hover-only 的功能在觸控裝置等於不存在（第四層已講），響應式要再確認：
  桌機靠 hover 展開的選單/工具提示，手機要有 tap 版本。
- 底部操作區（送出/確認鍵）避開手機瀏覽器底部工具列會蓋到的區域；重要
  的確認鍵放拇指容易搆到的下半屏，不是最頂端。
- 表單輸入框在 iOS 上 `font-size` < 16px 會觸發自動放大跳版——金額/帳號
  這類輸入框字級不要低於 16px（或 1rem）。

## 六、驗收（接回本 repo 既有標準）

- 改完在手機斷點、平板斷點、桌機斷點各看一次，確認版面只在設計好的斷點
  重排，中間尺寸不破版。
- 放大瀏覽器到 200% 看文字有沒有跟著變大（驗證 clamp 有 rem 成分）。
- 流體字級的最小/最大端點都是既有 token 階，沒有新增任意 px。
- 同一元件若用了 container query，丟到寬欄和窄欄各看一次。
