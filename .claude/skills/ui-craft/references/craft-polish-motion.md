# 打磨細節、動效、既有優先、驗收測試

## 既有優先：native → 既有 class/元件 → 手刻是最後手段

這是 CLAUDE.md 鐵則「CSS 復用優先」的具體落地順序，動手刻任何互動元件前照這個
順序檢查：

1. **先用瀏覽器原生元素**：`<button>` 就是按鈕、`<a>` 就是連結、
   `<input>`/`<dialog>`/`<details>` 原生就有。不要用 `<div onclick>` 重做平台
   已經免費提供的東西——這樣會失去 focus/keyboard/語意。
2. **本版本既有的共用 class／元件**：這個 repo 每個版本的 `site.js`、
   `main.css`、`design-system/components.css`（v3）已經有彈窗/tab/輪播/表單的
   共用實作，新頁面/新區塊要用到同類元件，先找既有的套用或擴充，不要重寫一份
   平行的實作。
3. **手刻只在真的找不到既有實作時做最後手段**，而且手刻就要補齊完整行為：
   鍵盤操作（方向鍵/Enter/Escape）、focus trap/return、完整 ARIA role/state、
   點外部關閉、彈窗要 scroll-lock。樣式好看但缺這些等於沒做完。

同樣的優先順序也適用在樣式本身：**既有共用 class → 既有 token 組合 → 真的需要
才新增一行 inline/局部樣式**，而且新樣式要綁定既有 token（`var(--color-*)`／
Tailwind 版本的 `bg-*`/`text-*` 這類語意 class），不要寫死顏色或 px。同一段樣式
組合如果在第二個地方重複出現，代表該抽成共用 class，而不是繼續複製貼上。

## 分層與深度（Subtle Layering）——規律應該「感覺到但看不到」

好的分層讓人只感覺到結構，不會特別注意到邊框/陰影本身在工作：

- **彈出層（dropdown/popover/modal）** 疊在觸發它的那層表面之上，层级要分得出來，
  不然視覺上會糊在一起分不出誰蓋在誰上面。
- **輸入框通常比周圍表面稍微暗一點**（凹陷感），不是比周圍亮——亮代表凸起，
  輸入框語意上是「接收內容」，凹陷感不需要很重的邊框就能傳達。
- **邊框應該是「找得到但不顯眼」**：低透明度的邊框顏色融入背景、只標出邊界，
  刻意調高對比的實色邊框反而顯得粗糙。
- **瞇眼測試（squint test）**：把眼睛瞇起來看畫面，應該還是看得出「這個在那個
  上面」「這裡是一個區塊的邊界」，但不會有任何東西突兀地跳出來刺眼。這個測試沒
  過，其他細節做得再多都沒用。
- **深度策略選一種就不要混用**：只用邊框（乾淨/工具感）、淺陰影（親切）、多層
  陰影（高級/有空間感）、表面色階差異（無陰影，靠色階區分前後）——四選一，整個
  版面/元件體系貫徹到底，不要卡片用陰影、按鈕又另外用邊框兩套邏輯並存。

## 打磨細節（Static polish）——靜態但容易漏掉的地方

- **同心圓角**：巢狀的圓角元素，外層圓角 = 內層圓角 + 內距，不要內外用一樣的
  圓角值——這是最常見讓卡片裡的卡片「看起來怪怪的」的原因。
- **等寬數字**：任何會變動的數字（倒數計時、賠率、金額、表格欄位）一律加
  `font-variant-numeric: tabular-nums`，避免數字跳動時整排寬度跟著抖動。
- **互動狀態缺一不可**：每個可互動元素都要有 default/hover/active/focus/
  disabled；資料類要有 loading/empty/error。缺任何一個狀態都會讓畫面感覺沒做完，
  是最容易被看出來「還沒做完」的地方。
- **點擊熱區最小 44×44px**（WCAG）、至少 40px——可見元件比這小（例如 20px 的
  checkbox）要用偽元素把熱區撐大，不要讓兩個熱區互相重疊。
- **陰影優先於邊框來表現「浮起」**：卡片/按鈕這類會浮起的元件，用多層半透明
  `box-shadow`（能適應任何底色），邊框留給分隔線跟 input 外框用。深色模式的陰影
  幾乎沒作用，分層要改靠邊框/亮度差異。
- **圖片外框**：疊加在使用者上傳圖片上的 1px inset 外框一律用純粹的
  `rgba(0,0,0,.1)`（淺色模式）/`rgba(255,255,255,.1)`（深色模式），不要用偏色的
  接近黑/白色——偏色看起來像圖片邊緣髒了而不是刻意的外框。

## 動效（Motion）——新增能力，過去這份技能完全沒涵蓋

動效要「感覺到、不是被盯著看」：夠快、有目的、絕不擋路。這個 repo 的輪播/tab/
彈窗/換膚切換這類互動都適用：

- **先問該不該動**：一天會被觸發上百次的操作（例如切換語言、高頻率的 tab 切換）
  **不要加動畫**，加了反而覺得變慢；偶發性的介面（彈窗、抽屜、toast 提示）用標準
  時長動畫；很少見的首次使用情境才考慮加一點驚喜感的動畫。
- **UI 動效時長一律 < 300ms**：按鈕按下回饋 100–160ms；tooltip/popover
  125–200ms；dropdown 150–250ms；modal/抽屜 200–500ms。180ms 的 dropdown 比
  400ms 的感覺靈敏得多。
- **用自訂的 ease-out，不要用瀏覽器內建的 ease-in**：進場/互動用
  `cubic-bezier(0.23, 1, 0.32, 1)`；畫面內移動用
  `cubic-bezier(0.77, 0, 0.175, 1)`（ease-in-out）。`ease-in` 會讓動畫一開始的
  那個畫面（使用者正在盯著看的那一刻）延遲才動，感覺遲鈍。
- **按壓回饋**：`:active` 時 `transform: scale(0.97)`（不要小於 0.95），給使用者
  「UI 確實接收到點擊」的觸覺回饋。
- **絕不從 `scale(0)` 開始動畫**——沒有東西是從無到有憑空出現的，起始狀態用
  `scale(0.95)` + `opacity: 0`。
- **彈出層要從觸發它的位置長出來**：`transform-origin` 設在觸發元素的位置，而
  不是從畫面中心長出來；modal 是例外，維持置中。
- **只對 `transform` 跟 `opacity` 做動畫**（GPU 合成）——對 width/height/margin/
  padding 做動畫會觸發 layout+paint，容易掉幀。絕不要寫 `transition: all`，一定
  要指名要動的屬性。
- **多個項目進場要有 30–80ms 的 stagger 間隔**，做出自然的依序出現感；離場動畫
  比進場更快、更內斂。
- **尊重 `prefers-reduced-motion`**：該情況下保留顏色/透明度過渡，拿掉位移動畫。

## 驗收測試——動手前講的「記憶點」要通過這四個測試才算數

延續 `../SKILL.md` 第二層「突破」一節的記憶點要求，交付前逐一核對：

- **互換測試（swap test）**：把你這次用的手法換成最預設、最常見的做法，畫面會
  不會變得沒差？如果互換後看不出差異，代表這裡其實是用了預設值，不是真的做了
  決定。
- **瞇眼測試（squint test）**：見上方「分層與深度」一節。
- **記憶點測試（signature test）**：指著畫面上具體 3–5 個地方說「這裡是這次刻意
  做的那個決定」——答不出具體位置、只會說「整體感覺比較好」就是沒通過。
- **Token 測試**：把這次新增/用到的顏色、間距、圓角唸一遍，每一個都能對應到
  `references/repo-tokens-map.md` 裡既有的 token 名稱嗎？如果有任何一個是自己
  編的 hex/px，沒通過，要改成既有 token 或回報使用者討論。
