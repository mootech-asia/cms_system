# 金融介面信任感（儲值／提款／註冊專用）

> 來源：這塊**沒有權威標準或口碑公開 skill**，搜到的多是實務部落格／廠商
> 內容（uxdesign.cc、phenomenonstudio、sennalabs 等），背後共通原則可對照
> Nielsen Norman Group 一向強調的「錯誤預防＋即時回饋」。因此這份只收
> **多個來源互相印證、且不牴觸本 repo 鐵則**的原則，廠商頁單方面宣稱的
> 轉換率數字（例如「信任標章 +23%」）一律不收（查不到原始研究）。
> 本 repo 的存款/提款/註冊頁用得到。

## 一、金額相關動作：確認 > 速度

- **送出前給一個 review 畫面**：把「金額＋方式＋手續費＋實收/實扣」清楚
  列出讓使用者過目再確認。金額類動作寧可多一步，不要一鍵就出去。
- **金額回顯**：確認畫面把使用者剛輸入的金額原樣顯示出來（不要只說「確認
  提款？」），讓他看到小數點沒按錯——「小數點按錯一位＝真的賠錢」。
- **新收款對象/新帳號雙重確認**：第一次用的提款帳號比既有的多一道確認。
- **手續費/到帳時間透明**：有手續費就在確認前列清楚，不要出帳後才發現被扣。
  透明＝使用者有掌控感＝信任。

## 二、狀態回饋：即時、明確、不自打臉

- 送出後**立刻**給處理中/成功狀態，不要讓使用者盯著沒反應的畫面猜「到底
  送出了沒」。延遲或前後不一致的確認，反而摧毀這個確認本來要建立的信任。
- 成功訊息用具體過去式（「已送出提款申請 NT$1,000，預計 XX 到帳」），不是
  只有一句「成功」。接第七層 UX 文案的成功訊息規則。
- 餘額若在存款後會變，可以短暫動一下餘額數字讓使用者看到錢進來了（動效
  時長仍走第三層 <300ms、`tabular-nums`）。
- 失敗要說清楚**為什麼失敗＋下一步**（餘額不足/超過限額/需補驗證），不是
  只丟「交易失敗」。接第七層阻斷性錯誤的三段式。

## 三、安全信號：真材實料，不做假

- 鎖頭圖示、加密提示、「已驗證」標籤這類信號使用者會據以判斷可不可信——
  但**只能在真的成立時才放**：真的走 HTTPS、真的有該驗證步驟才顯示對應標章。
- **禁止為了「看起來安全」擺假的安全標章/假的 SSL badge/假認證 logo**——
  這跟第二層「禁止編造假資料」「禁止冒充真實組織/記錄」是同一條紅線，也是
  本環境系統規則明訂不得產生的內容。缺真實憑證要回報使用者，不要自己貼圖。

## 四、錯誤預防（金額場景非選配）

- 確認模式＋可復原（undo/取消待處理申請）在金錢場景是基本盤，不是加分項。
- 金額輸入框：限制只能輸入數字/小數、即時格式化千分位、明確顯示幣別與
  限額範圍；iOS 上字級 ≥16px 避免自動放大（見響應式參考）。
- 送出鍵在請求進行中要 disable＋顯示處理中，避免使用者連點重複送出
  （重複出款是真的災難）。

## 五、本 repo 界線（必讀）

- 這份講的是**版面/狀態/互動**層面的信任感做法，**不碰文案的既有內容**：
  既有頁面的既有金額文案、條款文字一律逐字保留（第七層紅線），這裡的
  文案原則只適用**新寫**的狀態訊息。
- 不新增任何後端邏輯/假的驗證流程來「演」出安全感——只做前端真實狀態的
  清楚呈現。缺真實後端行為的，回報中標「佔位」（CLAUDE.md 回報規則 14）。

## 六、驗收

- 金額動作有沒有 review/確認畫面、有沒有原樣回顯金額？
- 送出後是否立刻有狀態、成功訊息是否具體、失敗是否給原因＋下一步？
- 有沒有擺任何「無真實憑證支撐」的安全標章？（有＝違規，拔掉）
- 送出鍵請求中是否 disable 防重複送出？
- 新寫的狀態文案有沒有掛 `data-i18n`、四語都寫？既有文案有沒有被順手改到？
