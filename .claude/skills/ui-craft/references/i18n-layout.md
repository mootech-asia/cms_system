# 多語言排版——換了字之後版面會不會爆

`cms-scaffold` 技能已經講清楚「怎麼讓每個語言的字正確換上去」（`data-i18n` 屬性 +
`applyLocale()`）。這份補的是上一層：**版面本身能不能撐住不同語言的字長差異**，這是
純粹的視覺/排版問題，跟 i18n 機制無關，所以放在 `ui-craft` 而不是 `cms-scaffold`。

## 核心問題：同一句話，不同語言長度差很多

同樣語意的句子，泰文/韓文排出來常常比中文/英文長 20–50%。本 repo 實際的語言組合
（zh/en/ko/th）裡，韓文、泰文最容易把「照中文字數抓的寬度」撐爆：

- 按鈕/badge 這類**固定寬度**（`width: 80px` 這種寫死數字）在中文下看起來剛好，
  換成韓文/泰文常常文字被截斷或溢出邊界。
- 導覽列/tab 的項目如果是**等分寬度**（`flex: 1` 平均分配），語言一換，原本對齊的
  文字基準線會跟著亂。

**設計時的因應方式**（不是改 i18n 機制，是排版本身要有餘裕）：

- 按鈕/badge/輸入框的寬度盡量讓內容決定（`min-width` + 內距，而不是寫死 `width`），
  真的需要固定寬度的地方（例如要對齊的表格欄位），寬度抓的基準要用**本 repo 四種
  語言裡最長的那個**，不要只用中文或英文量測後就定案。
- 過長文字的最後手段是 `text-overflow: ellipsis` + `title` 屬性顯示完整內容，但這
  是補救措施，不是預設做法——優先讓版面本身有彈性，而不是讓文字被截斷。
- icon 搭文字標籤時，不要假設文字永遠只有一行高度——行高抓的空間也要有一點餘裕，
  韓文/泰文某些字元的視覺高度跟中文不完全一樣。

## 文字一律是真文字節點，不要烤進圖片裡

本 repo 的翻譯機制（`data-i18n` 掃描 DOM 文字節點/屬性）**只對真正的 HTML 文字節點
跟屬性有效**。如果哪個畫面把文案直接烤進圖片（例如用圖片做的促銷 banner 上面寫死
英文字），`data-i18n` 完全碰不到它——這不是翻譯沒做完，是這個文字從一開始就不可能
被翻譯到。遇到這種素材，要嘛跟使用者確認有沒有可編輯的文字版本可以疊加在圖片上方
（HTML 文字 + 背景圖），要嘛明確回報「這塊文案鎖死在圖片裡，無法多語系化」，不要
假裝它已經處理好。

## 視覺驗收要用「本頁用得到的最長語言」測試，不是只測預設語言

本 repo 的驗收標準（CLAUDE.md）要求轉換前後同斷點截圖做 pixel-diff，這件事預設只會
測到當時畫面顯示的那個語言。**版面是否撐得住文字變長**是另一道需要額外測的項目：

- 做完一個頁面/區塊的視覺調整後，額外切到韓文或泰文（`cms-scaffold` 稽核方法論裡
  已經有切換語言的做法，照搬即可）看同一個斷點，確認沒有文字被裁切、沒有按鈕被撐
  到換行、沒有版面跑掉。
- 這項檢查跟 `cms-scaffold` 的「殘留語言稽核」是兩回事：稽核找的是「這裡沒翻譯到」，
  這裡找的是「翻譯到了，但排版撐不住」。兩者都要做，不能只做其中一個就算過關。

## 數字/金額格式：改版面不要順手改格式

這個 repo 是投注類 CMS，賠率/金額/倒數計時這類數字對不同語言/地區可能有不同的千分位
或小數慣例。做視覺調整時如果連帶看到數字格式，**不要順手「修正」成自己覺得對的格式**
——这跟 CLAUDE.md 驗收標準「內容逐字保留，不做任何順手改寫」是同一條界線，格式差異
可能是刻意設計，不確定就跟使用者確認，不要自己決定改掉。
