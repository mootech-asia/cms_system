# UX 文案——新寫的訊息/空狀態/通知怎麼寫

## 先搞清楚範圍：這份只管「新寫的文案」，不是「改既有文案」

**這份參考資料只適用於你要新增的功能/頁面需要寫全新的錯誤訊息、空狀態、成功訊息、
通知文案的時候。** 如果任務是轉換/遷移既有頁面（例如 v1.5~v3 轉 Tailwind），既有
文案一律照驗收標準「逐字保留，不做任何順手改寫」——發現某句錯誤訊息寫得不好、語氣
生硬，**不代表可以順手照這份文件的標準去「優化」它**，那是順手改寫，直接違反
CLAUDE.md 的驗收標準。只有在使用者明確要求新增文案、或新建一個這個 repo 原本沒有
的功能時，才套用下面的模式。

## 語言範圍：這裡的文字模式語言無關，數字門檻跟字數無關

本 repo 用 `data-i18n` 支援 zh/en/ko/th 四種語言。寫新文案時：

- 下面的「結構模式」（什麼失敗+為什麼+怎麼辦）跟語言無關，四種語言都適用。
- 原文附帶的英文字數門檻（例如「按鈕 2–4 個字」「錯誤訊息 12–18 個字」）是針對
  英文單字計算的，中文/韓文/泰文沒有對應算法，**不要照搬這些數字**，只取背後的
  原則：按鈕文字要短、錯誤訊息要把最重要的資訊放前面、整句話要能一眼掃完。
- 新文案一樣要掛 `data-i18n`、四種語言都要有對應翻譯值，寫完之後比照
  `references/i18n-layout.md` 的作法，切到韓文/泰文看會不會把按鈕/badge 撐爆。

## 錯誤訊息：結構是「什麼失敗＋為什麼＋怎麼辦」

**絕對不要只寫「發生錯誤」「操作失敗」這種沒有資訊量的訊息**，也不要用技術錯誤碼
（`Error 403`）或帶指責意味的字眼（「無效輸入」「不合法字元」）。

### 表單驗證錯誤（inline，欄位旁邊即時顯示）
簡短、具體說明該欄位要求什麼，不需要完整三段式：
- 「Email 需要包含 @」
- 「密碼至少需要 8 碼」
- 「請選擇未來的日期」

### 系統/可恢復錯誤（modal 或 banner，後端操作失敗時）
格式：`[動作失敗]。[可能原因]。[復原方式]。`
- 「儲值失敗。您的卡片遭拒。請改用其他付款方式。」
- 「無法儲存變更。連線中斷，請重新連線後再試一次。」

### 阻斷性錯誤（整頁/大型 modal，使用者完全無法繼續操作時）
格式：`[被阻擋的是什麼]。[原因]。[需要的具體動作]。`
- 「需要重新驗證。請確認您的 Email 才能繼續使用功能，請查看您的信箱。」
- 「系統維護中。預計 15 分鐘後恢復，您的資料不會受影響。」

**核對清單**：有沒有用指責性字眼（避免）？有沒有說清楚具體問題（避免「發生錯誤」
這種空泛說法）？有沒有給出明確的下一步？語氣是不是主動且不卸責（「我們無法儲存」
優於「變更無法被儲存」）？

## 空狀態：解釋為什麼是空的＋給一個明確的下一步

**不要只寫「尚無資料」「沒有記錄」**——這對投注記錄/交易記錄這類頁面尤其重要
（本 repo 的 `betting-record.html`／`deposit-record.html` 這類頁面如果要新增一個
「目前沒有任何記錄」的空狀態，套用下面任一種）：

- **首次使用**（使用者還沒有任何記錄）：說明空的原因 + 能帶來的好處 + 具體行動。
  例：「還沒有投注記錄。開始您的第一筆投注，記錄會顯示在這裡。」
- **使用者已清空**（例如篩選後剛好沒有本月記錄）：正向確認 + 說明新內容什麼時候
  會出現。例：「這段期間沒有交易記錄。選擇其他日期範圍查看歷史紀錄。」
- **搜尋/篩選沒有結果**：說清楚找的是什麼沒找到 + 給替代方案。
  例：「找不到符合「OOO」的遊戲。試試其他關鍵字，或瀏覽全部遊戲。」

## 成功/確認訊息：過去式＋具體說明完成了什麼

格式：`[動作] [結果/效益]`，不要只回「成功」兩個字：
- 「變更已儲存」優於「成功」
- 「儲值已完成，餘額已更新」優於「操作成功」

高風險動作（刪除帳號、確認出款）的確認訊息要講清楚後果，不要用可能被誤解的委婉說法：
「確定要刪除帳號嗎？所有資料都會遺失，且無法復原。」

## 語氣要跟著使用者當下的情緒走

同一個品牌的「聲音」（voice）維持一致，但「語氣」（tone）要隨情境調整：

| 使用者情緒 | 情境 | 語氣 |
|---|---|---|
| 挫折 | 錯誤、失敗、被阻擋 | 同理、聚焦解法，不指責使用者 |
| 困惑 | 第一次使用、複雜功能 | 有耐性、步驟拆解清楚 |
| 從容 | 例行操作、回訪使用者 | 簡潔直接，不需要多餘說明 |
| 謹慎 | 高風險動作（刪除/出款確認） | 嚴肅、交代清楚後果，不誘導 |
| 完成 | 動作成功、達成目標 | 正向、簡短，程度跟動作重要性成比例 |

## 無障礙：文案本身也要顧到

- 按鈕/連結文字本身要說清楚動作是什麼，不要只寫「確定」「點這裡」——螢幕閱讀器
  使用者是跳著聽連結文字列表，「查看隱私權政策」比「點這裡」有意義得多。這跟
  `references/aria-patterns.md` 的 `aria-label`／可存取名稱原則是同一件事，只是
  從文案本身解決，不用額外加 `aria-label` 補救。
- 不要只靠顏色傳達錯誤/成功——文字本身要講清楚是哪一種狀態（「錯誤：Email 為
  必填」搭配錯誤圖示，而不是只有紅色文字本身）。
